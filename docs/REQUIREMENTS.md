# 需求分析 — sing-box 线路自动优选守护

## 1. 背景
家庭透明代理网关 88.4（iStoreOS / sing-box-extended）有 12 条出网线路，分三类载体：
UDP 系（`cc-bond`/`cc-hy2`/`cc-tuic`/`rn-*`）、TCP 系（`cc-reality`/`cc-xhttp`）、独立兜底（`warp-direct`）。

现用内置 `urltest` + 人工评估，缺陷是**只测握手延迟，与吞吐排序相反**，且偏向 TCP。
用户已确立硬规则：**UDP 优先，TCP 永不自动当主力**。

## 2. 目标
- **G1** 基于**真实吞吐**评估线路，而非握手延迟
- **G2** 通过 sing-box Clash API **实时切换**，让在用协议始终最优
- **G3** 严格表达「UDP 优先」：TCP/兜底仅在 UDP 全线不可用时启用
- **G4** 零第三方依赖（Python 3 标准库）
- **G5** 零配置侵入：只调 API，不改 `/etc/sing-box-config.json`
- **G6** 可随时停用，停用后退回静态优先级链 `fb-main`

## 3. 非目标
- 不做流量统计/计费
- 不改动服务端（148/107）配置
- 不替代现有 watchdog（职责互补：watchdog 管存活，本守护管选优）

## 4. 功能需求
| ID | 需求 | 优先级 |
|---|---|---|
| FR1 | 周期采集各线路连通性与失败率 | P0 |
| FR2 | 周期采集各线路**真实吞吐**（分片下载计时） | P0 |
| FR3 | 综合评分（吞吐 0.6 / 延迟 0.2 / 成功率 0.2） | P0 |
| FR4 | UDP 优先硬约束：候选池仅 UDP 系 | P0 |
| FR5 | 迟滞：挑战者连续 2 轮领先 >20% 才切 | P0 |
| FR6 | 限频：切换间隔 ≥ 5 分钟 | P1 |
| FR7 | 手动覆盖保护：用户手切过的 selector 不被改写 | P0 |
| FR8 | 回归保护：切换后 60s 失败率上升则回退并拉黑 30 分钟 | P1 |
| FR9 | 全局故障保护：全线失败判定为本地网络问题，保持现状 | P0 |
| FR10 | 状态与历史落盘，决策可审计 | P1 |
| FR11 | 全线失败推送告警（QQ） | P2 |

## 5. 非功能需求
| ID | 需求 |
|---|---|
| NFR1 | 仅用 Python 3 标准库 |
| NFR2 | 不修改 sing-box 配置文件，只调 HTTP API |
| NFR3 | 探测**不得干扰生产流量**（独立探测路由，见设计 §4） |
| NFR4 | 单次运行 < 60s，开销可忽略 |
| NFR5 | 崩溃不影响出网（降级为静态优先级链） |
| NFR6 | 决策可解释：日志含原始指标与评分 |

## 6. 约束
- 88.4（iStoreOS）**无可用 python3、无 jq** → 守护部署在 **88.10**（Ubuntu）
- 88.4 Clash API 监听 `0.0.0.0:9090`
- 探测目标域名必须命中代理规则集，否则走 direct 测不到线路
- bond 延迟 = 两条子隧道之和，不得与单协议直接比延迟

## 7. 验收标准
- **AC1** 产出 12 条线路真实吞吐排名（M1 交付物）
- **AC2** 守护连续运行 24h 无异常退出，日志完整
- **AC3** 人为断掉最优线路，2 个周期内切到次优
- **AC4** 手工切换某 selector 后，守护不再改写它
- **AC5** 停用守护后 `fb-main` 静态链正常
- **AC6** UDP 全线不可用时流量落到 TCP 系，不停网
